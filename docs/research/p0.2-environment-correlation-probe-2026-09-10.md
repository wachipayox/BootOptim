# P0.2 pre-entrypoint environment correlation probe — 2026-09-10

Status: **ACTIVE DIAGNOSTIC / P0.2 OPEN**

This record does not identify or optimize the P0.2 root cause. Physical controls with the same intended configuration have placed `mod_entrypoint` between 139.477 s and 241.540 s (102.063 s range), while the post-entrypoint interval varied by only about 8 s. Later normal traces put entry around 190–202 s and attributed roughly 44–51 s of a pre-entry launcher/Mixin interval, but did not reproduce the extreme slow control. Existing ETW evidence contains both Java and HDD activity and does not justify a Defender-only explanation.

The purpose of this probe is to make the next naturally occurring fast/normal/slow observation comparable enough to decide whether the pre-entry variance tracks JVM work, class-loading volume, GC, storage/page-in pressure, or external Windows pressure. It is not an A/B mechanism and no physical run is requested by this branch.

## Constraints inherited from earlier tracing

PR #207 established useful causal launcher boundaries but also showed that a cross-thread phase is not task CPU. PR #228 then proved that the old strict Bootstrap-transform-accept to Bootstrap-entry interval contains two separate requests: Mixin's transformed-byte side request and the later real classloading request. Its exact diagnostic fork is valuable for hosted attribution but StackWalker/per-target logging has observer cost and is not the right physical P0.2 sampler. PR #230 further narrows the hosted Mixin/Main lifecycle without changing scheduling. None of these profiles reproduced the 241.540 s entrypoint outlier.

`docs/research/laptop-host-trace-2026-09-07.md` already added a bounded WMI host sampler, but its original schema does not carry explicit measurement origin/endpoint/cold-state provenance, exact JVM clock alignment, target read/write split, disk queue/read latency, standby-cache state, or observer-cost fields. The new P0.2 probe is a separate diagnostic so the existing generic host tracer's contract is unchanged.

## Implemented probe

### 1. Coarse JVM snapshots, default off

`-Dboot_optim.p02JvmProbe=true` adds snapshots only at already-existing coarse boundaries:

- transformation-service construction;
- transformation-service initialize;
- transformation-service onLoad;
- BootOptim `mod_entrypoint`;
- `main_menu` when the normal startup profiler/report path already reaches that hook.

Each `BOOTOPTIM_P02_JVM` row records JVM uptime and start epoch, process CPU duration, current/total/unloaded class counts, aggregate GC count/time, heap used/committed and thread count. It does not log individual classes, walk stacks, start JFR, run `jcmd`/`jstat`, wrap classloaders, touch executors, or read resources. Failures are fail-open and emit only the exception class.

The management-bean accesses themselves are observer work. Therefore **any run with `p02JvmProbe=true` is diagnostic and cannot be used as a clean TTMM benchmark sample**. Normal/default-off behavior remains unchanged.

`jvm_start_epoch_ms` is the synchronization key for external samples. It lets the offline parser map a UTC WMI sample onto JVM uptime without deriving startup from log timestamps or from Prism launch time.

### 2. External Windows sampler

`tools/laptop-bench/remote_laptop_p02_probe.ps1` attaches only after the transaction runner has established the exact Java PID and `CreationDate`. Default cadence is 5 s. It never reads Minecraft logs, the instance, mods, resource packs or Prism while sampling.

Per sample it records:

- target Java CPU, read/write/other I/O rates, page-fault rate, private working set/private bytes and thread count;
- available memory, system cache, standby-cache buckets, modified-page-list bytes, pages input/read and transition-fault rates;
- total physical-disk read/write rates, operations, current/average queue, average read latency and disk utilization;
- total CPU and Windows processor queue length;
- WMI sample cost.

Header fields make `origin`, `endpoint` and `coldState` mandatory. The footer records total observer CPU and maximum sample cost. PID reuse is rejected through the PID/creation tuple. The script changes no process priority, affinity, power policy, cache state or benchmark endpoint.

### 3. Offline correlation

`tools/laptop-bench/p02_correlate.py` consumes only completed console/startup/host files. It checks one JVM start epoch, one mod-entry snapshot, explicit provenance, endpoint availability and host coverage. It partitions external samples at `mod_entrypoint`, summarizes the pre-entry and post-entry signals separately, and computes coarse JVM deltas from the earliest service snapshot to mod entry.

The parser intentionally does not classify a root cause. In particular, it refuses the common invalid inference `wall - process CPU = disk`, and documents that process page faults alone are not hard-fault proof.

## Required evidence for a future physical P0.2 observation

A physical sample may enter the P0.2 correlation corpus only when all of the following hold:

1. **Identity/provenance:** transaction state proves the expected interactive session, exact Java PID + `CreationDate`, no surviving target Java before launch, expected Java executable, required JVM arguments exactly once, no stale forbidden BootOptim argument, exactly one packaged BootOptim wrapper, and a stored SHA-256 of the effective command line rather than its raw/token-bearing contents.
2. **Software contract:** BootOptim artifact SHA-256, exact pack/resource-selection result and effective resource order are retained. Missing or duplicate startup markers, resource-selection divergence, stale Prism state, multiple Java processes or timeout invalidate the sample.
3. **Origin:** `origin=physical_laptop`. Hosted Linux exact-pack and `hosted_windows_harness` observations are separate populations and may validate tooling but cannot close physical P0.2.
4. **Endpoint:** choose and record exactly one endpoint (`main_menu` or `main_menu_presented`). Compare only identical endpoints. `mod_entrypoint` is the required internal split, not the overall endpoint.
5. **Cold-state class:** one of the following must be recorded before interpretation:
   - `fresh_boot_no_pack_touch`: same recorded Windows boot, and since that boot there has been no prior Prism launch of this instance, Minecraft Java launch, deliberate pack-directory traversal/hash, cache purge, or manual AV scan of the pack. This is an operator provenance assertion, not proof that Windows background services never touched a file.
   - `warm_same_boot`: at least one prior launch/touch of the exact instance occurred on the same Windows boot.
   - `unknown`: provenance cannot establish either state. Such a run can diagnose itself but must not be compared as a cold/warm pair.

Never purge the standby list or otherwise manufacture a synthetic cold cache for this investigation. That changes the environment being diagnosed. `windowsBootUtc` and the declared cold-state class are retained so cold/warm/unknown samples cannot be silently pooled.

6. **Clock/coverage:** successful P0.2 JVM snapshots must share one `jvm_start_epoch_ms`; the external sampler's first sample must be no later than 15 s after JVM start and sampling must continue through the declared endpoint/process exit. A trace with missing early coverage is insufficient for the 100 s pre-entry question.
7. **Observer budget:** retain `observerCpuMs`, per-sample cost and cadence. The correlator warns if the sampler averages over 2% of one logical CPU across its sampled wall or if a WMI sample consumes over 20% of the interval. Such a trace may still explain an instrumentation problem, but is not low-noise P0.2 evidence.
8. **Offline bundle:** preserve complete process console through exit, `bootoptim-startup.log`, normal `latest.log`, transaction state, host JSONL, correlation JSON, resource-selection check/effective options/config needed by the existing harness, BootOptim JAR hash, Java version/executable identity and command-line hash. Analysis occurs only after Java exits; no log polling is introduced.

A single outlier can show temporal correlation but cannot establish causality. To attribute P0.2, the corpus must eventually contain the outlier and at least one normal observation produced by this same schema with matching physical origin, endpoint, pack/JVM contract and cold-state class. That is repeated unchanged diagnostic observation, not a candidate/control optimization A/B.

## How to interpret the same-schema corpus

- **Process/JVM CPU:** compare pre-entry wall against `process_cpu_ms` delta/effective CPU cores. A wall expansion with comparable class count but proportionally larger CPU indicates additional/slower JVM-side work; a large wall expansion without process CPU growth points to waiting/descheduling/I/O rather than CPU work alone.
- **Classloading:** use `total_loaded_classes` delta as workload volume, not timing. A slow run with materially more classes indicates a different load path/state. Similar class volume plus elevated page-in/disk pressure is compatible with the same class path running against a colder/slower storage state.
- **GC:** compare GC count/time and heap deltas. GC is sufficient to explain extra wall only to the extent the additional GC time is actually of comparable magnitude; do not infer from collection count alone.
- **Disk/page cache:** require joint evidence. Page faults alone are insufficient; stronger storage evidence is aligned rises in PagesInput/PageReads, Java read rate, disk read rate/queue/read latency and cache/standby movement during the pre-entry window.
- **External Windows pressure:** high total CPU/processor queue or total disk pressure while Java's own CPU/I/O stays low supports external contention/descheduling. The generic counters cannot identify Defender specifically. A Defender attribution would require provider/process-specific ETW or equivalent evidence aligned to the same window.

## Decision gate

P0.2 remains **OPEN**. No production optimization follows from this branch. The next optimization hypothesis is allowed only after a same-schema physical corpus captures the variance and one mechanism accounts for a material share of the extra **pre-`mod_entrypoint`** wall without violating the origin/endpoint/cold-state rules above. Hosted traces remain architectural evidence and tooling validation, not a substitute for the missing physical outlier.
