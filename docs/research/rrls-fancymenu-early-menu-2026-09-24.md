# RRLS 5.0.11 and the FancyMenu title boundary — 2026-09-24

Status: **RESEARCH / do not ship RRLS's early-menu path with this pack**. This is a fast-PC visual report plus log/source attribution, not a controlled RRLS performance A/B or a fix validation. No laptop was used.

## Reproduction and evidence

The user launched `C:\Users\Wachii\AppData\Roaming\.minecraft_welite_beta_nooptim` on the fast PC with `rrls-5.0.11+mc1.21.1-forge.jar`, the controlled `FancyMenu 3.9.0-wedit` JAR, no BootOptim JAR, and `config/rrls.toml` containing `hideOverlays = "ALL"`, `miniRender = true`, `type = "PROGRESS"`, `reInitScreen = true`, `skipForgeOverlay = false`. The user saw a broken first title screen which repaired after background loading, no RRLS progress overlay, and a several-second freeze near the end of a manual resource-pack reload. RRLS source references must use the 1.21.1 **backport** tree at <https://github.com/dima-dencep/rrls/tree/1.21.1/backport> and be checked against the installed JAR's bytecode. The public tag named `1.21.1-5.0.11` currently exposes newer `GuiGraphicsExtractor`/`Identifier` source that does **not** match the installed 1.21.1 JAR's `GuiGraphics`/`ResourceLocation` bytecode. The local FancyMenu fork source is `C:\Users\Wachii\OneDrive\Documentos\.Minecraft modding\FancyMenu`.

The manual FancyMenu preload spans **6.048 s** on the Render thread, including a **5.575 s** interval to the prelaunch marker. It is a strong explanation for the reported final freeze, but no frame trace was captured, so it is not a measured freeze duration. Total manual reload to FancyMenu-finished is **29.339 s**; do not conflate it with the final freeze. The initial one-layout filter is intentionally restricted to the first reload in `MixinMinecraft.java`; later reloads use `ResourcePreLoader.preLoadAll(120000)` with the complete list. This matches the 20/2/130 marker. The user-owned FancyMenu fork is the appropriate place to change this policy, with layout-selection and invalidation guarantees; a BootOptim-side early return from `preLoadAll` was already rejected in PR #116, and cooperative wait was rejected in #117.

RRLS's `MinecraftClientMixin` suppresses the constructor's loading message and can call `onResourceLoadFinished` early under the hidden-initial state. Its `ReloadableResourceManagerMixin` constructs a provisional manager and quick-reloads only a subset of UI listeners. FancyMenu registers after those quick reloads and finishes its listener only in the full reload. Therefore the visible menu-before-FancyMenu-finished interval is structurally possible and agrees with the user's visual report. The log does not contain a reliable first-visible-frame marker, so it does not establish the exact duration of the broken title. The RRLS source does not expose an atomic old-generation/new-generation commit for arbitrary mod listeners. A compatible design would keep the initial loading screen until required title consumers, including FancyMenu's selected layout and its resources, complete; manual reload could render the existing generation only if every active renderer has a safe lifetime and the new generation is committed in order on the render thread. This is a new architecture, not a safe configuration of the current quick-reload hook.

The user-owned FancyMenu fork makes this boundary explicit: `ScreenCustomizationLayer.shouldCustomize()` returns false before its **full initial** Minecraft reload finishes unless a layout requests `loadEarly`. Its listener is registered directly during `Minecraft.resizeDisplay`. The installed RRLS 1.21.1 JAR quick-reloads only hard-coded Font, Language, Splash and GUI Sprite listeners; it has no generic FancyMenu early-listener registry, as verified against the 1.21.1 backport source and installed `ReloadableResourceManagerMixin` bytecode. On a later reload, FancyMenu's `ResourceHandlers.reloadAll()` calls `releaseAll()` on the image, audio, video and text handlers, closing resources in their mutable maps before the new preload. Thus continuing to render the old menu while this code runs is not a retained-old-generation implementation. The exact pack title also contains item and player-entity widgets (PR #125), so title readiness is wider than its panorama and font alone.

This supports two independent work streams. First, an opt-in FancyMenu-fork experiment can extend the existing selected-layout plan to post-initial reloads, but it must account for the *currently visible screen* and all backgrounds it may use, not blindly filter to `title_screen`. It must preserve `randomOnlyFirstTime` picks and fail open to the full list when provenance is uncertain. This may remove the observed six-second final preload while keeping the stock reload overlay. Second, early usable title requires a resource-generation contract across Minecraft/NeoForge and FancyMenu: prepare the title's dependencies first, publish them only after their ordered render-thread commit, keep the old generation alive during manual reload, and gate world entry on world-required resources. RRLS's current early menu and existing FancyMenu preload cannot provide that contract by themselves. A usable-menu timestamp must be measured separately from full reload completion; permitting navigation before completion is plausible, but unrestricted world join is not yet established safe.

The absence of a mini progress bar is **unresolved from logs**. With `miniRender = true` and `type = "PROGRESS"`, RRLS's `GameRendererMixin` intends to call `overlay.rrls$miniRender` only when the overlay has the HIDE rendering state. Its NeoForge overlay mixin has a separate early-display path and can choose normal superclass rendering or change state later. No `Failed to draw overlay!` error appears, but there is no per-frame state trace. The config value `hideOverlays = "ALL"` selects hiding on initial load as well as reload; it does not by itself prove that the mini bar rendered or failed.

## Decision and next gate

Do not port RRLS's current `hideOverlays=ALL` early-menu behavior into BootOptim. A narrowly safer RRLS configuration for a future local check is `hideOverlays=RELOADING`, preserving the initial loading barrier, but its manual reload behavior and FancyMenu freeze still require visual validation; it is not a production solution. The controlled FancyMenu fork could instead extend its provenance-aware selected-layout preload to manual reloads while preserving the currently displayed generation until ordered commit. Before implementation, audit how `ResourceHandlers.reloadAll()` invalidates active textures and how FancyMenu reselects the current random layout, then validate initial title, changed resource-pack selection, manual reload, and representative world/menu use. No laptop run is justified until a fast-PC visual pass succeeds.

## Selective menu-ready barrier hypothesis

The user's proposed BootOptim variant would discover the active title's consumers, prepare/commit their transitive resource dependencies in the foreground, present the menu only after those are drawable, and continue unrelated reload work in the background. The current trial shows why the boundary must be *draw-ready*, not merely layout-ready: panorama, logo, buttons and ToadLib config can be brought forward, while players and item icons are still absent. FancyMenu's active layout directly exposes player elements and the six decorative item IDs, but arbitrary mod-contributed title widgets (here Create's goggles) also need to declare or be traced for dependencies. Dynamic observation of a missing icon alone cannot identify its complete model/sprite graph.

Minecraft's `ModelManager` prepares atlas stitch results and bakes models against sprites from those results, then uploads atlas textures in its apply stage. The current API does not publish a separately drawable model for one menu item before that apply; merely prioritizing six model JSON reads does not make their sprites available. A credible prototype therefore needs either a small independently published menu model/atlas generation with safe handoff to the full generation, or a measured proof that moving the full relevant model/atlas apply before menu presentation is still worthwhile. Entity rendering has its own shader/skin/model-layer dependencies. Unknown mod callbacks must fail open to the normal barrier. During a manual reload, the old visible generation must remain alive until the replacement is committed; FancyMenu's current `releaseAll()` path does not provide this.

This is an architectural candidate, **not an accepted optimization**. The next gate is to identify the first-draw dependency for the player row, measure the minimum model/atlas work pulled into the menu barrier, and compare process-origin-to-*visually complete* menu time against the stock full-reload path. A menu that is clickable sooner but visually incomplete fails this pack's stated goal. World entry must wait for world-required resources even if title navigation is allowed sooner.
