## MCEF interpretation

The MCEF first-consumer defer marker occurred before resource reload, but the actual MCEF/native initialization was observed after the menu. Therefore MCEF was not on this run's main-menu critical path. This does not prove that MCEF is harmless during world entry; it only separates it from the menu variance measurement.

## What this does and does not prove

The corrected harness confirms that the laptop's very long startup is concentrated in the resource/model pipeline, with ModelManager and its model bakery dominating the critical path. Existing laptop menu runs ranged roughly from 350 s to 380 s, so this single run cannot identify the source or distribution of run-to-run variance. It also cannot establish storage/page-cache causality.

The next useful experiment is a small repeated set using the same harness and no code changes, recording per-phase wall, process CPU, GC, heap and available-memory deltas. A candidate that changes only a subphase but not ModelManager completion or total menu time should not be promoted. If the variance correlates with GC/heap pressure, test allocation/GC and worker scheduling hypotheses before adding more mixins.

## Disposition

Keep this as diagnostic evidence only. Do not merge the variance logger into production and do not claim that the P0.2 root cause is solved. Reopen with repeated corrected runs, ideally after a controlled fresh boot/page-cache state, or with a diagnostic that samples worker queue saturation and disk/page-fault activity without adding a large startup burden.
