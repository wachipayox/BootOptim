# Non-ZIP PathPackResources enumeration catalogue — agent 215 (2026-10-11)

**Decision: REJECT the proposed persistent/stable-provider catalogue for the present PathPackResources domain.** Diagnostic source code is removed from the final PR. No production mechanism, default-off feature, cache, or profiler remains. **No performance candidate reached A/B**: the required provider-identity/mutability/invalidation precondition failed before implementing anything that could legitimately receive two controls and two candidates.

## Exact bounded front and repository history

Target: resource enumeration of the vanilla **exact** `net.minecraft.server.packs.PathPackResources` class, specifically `listResources(PackType, namespace, path, ResourceOutput)` and `getNamespaces(PackType)`. This is the path/UnionFS provider family used by mod/SecureJar resources, not `FilePackResources` direct ZIP enumeration; subclasses/custom providers are out of scope. An efficient catalogue could remove repeated discovery of paths only if entries, priorities, filtering, source state and invalidation were actually stable. No caller/pack/generation identity is accepted as sufficient without content-state proof.

Mandatory historical checks (open and closed, bodies/comments/results) include [#69](https://github.com/wachipayox/BootOptim/pull/69), [#71](https://github.com/wachipayox/BootOptim/pull/71), [#137](https://github.com/wachipayox/BootOptim/pull/137), [#140](https://github.com/wachipayox/BootOptim/pull/140), [#141](https://github.com/wachipayox/BootOptim/pull/141), [#142](https://github.com/wachipayox/BootOptim/pull/142), [#182](https://github.com/wachipayox/BootOptim/pull/182), [#264](https://github.com/wachipayox/BootOptim/pull/264), [#283](https://github.com/wachipayox/BootOptim/pull/283), [#285](https://github.com/wachipayox/BootOptim/pull/285), [#318](https://github.com/wachipayox/BootOptim/pull/318), [#326](https://github.com/wachipayox/BootOptim/pull/326), [#327](https://github.com/wachipayox/BootOptim/pull/327), [#329](https://github.com/wachipayox/BootOptim/pull/329), [#330](https://github.com/wachipayox/BootOptim/pull/330), [#331](https://github.com/wachipayox/BootOptim/pull/331), and [#332](https://github.com/wachipayox/BootOptim/pull/332). The integrated [#329](https://github.com/wachipayox/BootOptim/pull/329) ordered ZIP prefix index already removes central-directory scans for *other* providers; its hosted/physical 2C2B savings (343.987/286.159 ms and 281.25/484.375 ms actual owner CPU, respectively) cannot be transferred to PathPack. #142's ordered ZIP snapshot did not show a coherent final menu effect and retained heap/GC surface; #326's exact repeat memo had only 12 third-plus ZIP queries / 6.114 ms observed CPU, a distinct rejected mechanism.

[Path prefix IO audit](path-prefix-io-audit-2026-10-01.md) from #318 exercised SecureJarHandler 3.0.8's *real* UnionFS, actual reversed directories and mixed ZIP/directory bases, callback order and filter base/entry, changed filter decisions, fresh existence/attributes, create/edit/delete of a file with **the same pre-existing root/prefix**, reopened pack identity and embedded-ZIP closed errors: 174 contracts plus 8,000 concurrent reads passed. The CIT #264 empty-path probe calls listResources with an invalid empty path and returns/logs; it is not a reusable catalogue.

## Diagnostic method and gate (NOT performance A/B)

A temporary mixin on only the exact `PathPackResources` class called each stock method once and returned the unmodified original namespace Set. For list enumeration it passed a temporary delegate to the original method, forwarding each ResourceLocation and original IoSupplier to the original ResourceOutput **once, in original order**. Output callback CPU was timed separately and subtracted to avoid treating consumer execution as pure provider work. No new resource query, path snapshot, cache, worker, changed supplier, modified directory/filter logic or GL operation. Unknown subclasses took the stock method. Every method-level observation includes observer clocks/allocations and the temporary callback wrapper: these diagnostics are unsuitable as clean CPU performance votes, and a callback that introspects its caller/wrapper is an extra diagnostic semantic risk. That code is **not** retained in the final PR.

Minimum gate was specified in [diagnostic PR #340](https://github.com/wachipayox/BootOptim/pull/340) *before* Actions: Build/packaged bootstrap, vanilla startup, then a single hosted exact-pack `smoke` with `-Dboot_optim.profilePathPackEnumeration=true` and `-Dboot_optim.profileStartup=true`. Require nonzero activation, CPU availability, complete flush, no throws or inflight probes, exact pack selection/atlas/reload/menu and no BootOptim Mixin failure. Not enough for any speedup conclusion.

## Binary disposition, correctness risk and next decision

**Reject the specific catalogue mechanism for the presently identifiable PathPack provider.** A persisted/snapshot enumeration keyed by class, `PackResources` identity, `Path`, `PackType`, namespace, manager or resource-reload generation cannot prove freshness: files can appear/disappear/change beneath the same directory/root and a UnionFS filter may inspect current candidates, while their priority ordering and callback emission/supplier semantics must remain observable. Sharing a list also risks mutable collection identity. A full fresh scan to verify all entries/filters would consume the work the cache promises to remove. Reliable per-provider archive/directory versioning, exact stable identity and close/reopen invalidation were not established; therefore writing an optimistic caching branch would violate the stated safety gate. There is no stock-vs-index performance series. **2 controls / 2 candidates: N/A (0C/0B)**, appropriately blocked *before* any candidate; no fabricated performance win, loss or quantitative rejection. The 1.092 s diagnostic scope is neither a guaranteed ceiling nor proof of saving, and its Linux hosted scale does not rule out a distinct HDD effect.

Potential reopening requires an actually delimited immutable provider (not merely exact `PathPackResources` class), archive fingerprint/version or demonstrated immutable membership/filters with reliable pack-close and reload lifetime, current callback-priority-order and fresh supplier fidelity, and a **clean** no-observer benchmark of owner CPU inclusive of first build, guards, filtering and invalidation under identical workloads and 2C/2B opposite-order observations. Then check allocation/retained heap/GC/I/O and actual critical path if affected, ordinary startup and hosted exact-pack runtime. If effect is HDD/page-cache-sensitive or small, require a *separate valid physical* gate; none is offered or claimed here. Any unknown provider shape or filter state must fail open. No integration/merge of a runtime optimization is justified.

The final PR changes only this document and the research index; the temporary probe/mixin/profiler edits are absent from its final tree. There is no entry in `docs/optimizations` because nothing is retained. Principal's decision is solely whether to merge the documented rejection into `agent/integration-current`.
