# P0.2 harness hardening — 2026-09-10

## Scope

This is methodology evidence, not an optimization and not a time-to-menu result.
It records failures found while turning the laptop P0.2 investigation into a
reproducible diagnostic.

## Invariants

- Do not read Minecraft/Prism logs while a timed or diagnostic client is alive.
- Stage exactly one packaged bootstrap wrapper and validate its SHA-256 before launch.
- Bind Java to the interactive session, launch time, configured Java executable, creation time and
  validated JVM arguments before accepting a run.
- Treat process/observer failures as invalid evidence, never as performance values.
- Copy logs only after the validated Java process exits; restore the original wrapper and `instance.cfg`
  only when no owned Prism/Java process remains.

## Rejected instrument paths

1. `System.out` markers are not durable with Prism's `javaw`. P0.2 JVM snapshots now go through the
   Bootstrap startup report and the regular mod logger/report.
2. Detecting a launch only by `--gameDir`/instance-path text in `Win32_Process.CommandLine` rejected a
   real client that reached the menu. Prism's effective Java command does not reliably preserve that text.
   The runner instead uses session + launch-time + exact configured executable, then validates its full
   safe JVM-token contract before measurement.
3. An ordinary detached PowerShell child created avoidable lifecycle and `$Host` automatic-variable
   failures. The runner now registers the host observer as its own bounded interactive scheduled task
   after Java validation; it is not a child of the Java process or of an SSH session. This observer is
   diagnostic-only and disabled unless `P02HostProbe` is explicit.
4. `System.Diagnostics.Process.WaitForExit` was not reliable for this Java/Task Scheduler combination:
   a task could exit with code `1` or remain unfinalized after `javaw` had gone. The runner now polls a
   fresh process-table entry once per second, checking PID, executable process name and creation time.
   PID reuse or an unreadable identity invalidates the transaction; it never becomes a completed sample.
   The scheduled runner also writes `runner-output.txt` in the run directory so a non-zero task result
   has inspectable controller evidence without reading live Minecraft logs.
5. Prism owns the laptop heap through `OverrideMemory=true`, `MinMemAlloc` and `MaxMemAlloc`
   (currently 128/6144 MiB). Supplying `-Xms` or `-Xmx` through the transaction's `JvmArgs` opens
   Prism's warning dialog and invalidates unattended launch behavior. The transaction now rejects those
   flags before staging; heap changes belong to the Prism fields, not benchmark JVM arguments.
6. The original host probe used WMI performance classes every five seconds.  On the physical HDD laptop
   a sample itself reached 23 seconds, so it could materially perturb the client.  The retained probe
   uses `Get-Process` only, rechecks PID/start-time identity, captures cumulative target CPU/memory/thread
   snapshots every 30 seconds, and makes no WMI, disk, global-CPU, cache or log reads while Java is alive.
   It is intentionally a low-intrusion attribution aid, not a host-wide profiler.

## Operator workflow

1. Dispatch the transaction and record only state/process/task status while Java is alive. Do not tail
   `latest.log`, `debug.log`, Prism output or the host observer file at this stage.
2. Poll at a bounded cadence (normally 10--15 seconds externally; the runner's exit check is one
   second). A visible window is not completion evidence. Java absence plus a final `finished`/`invalid`
   state is required.
3. Only after that final state, inspect `runner-output.txt`, wait for the P0.2 observer task to finish,
   archive logs, correlate the files and restore the original wrapper/configuration. A task result of
   non-zero, `measuring` with no live recorded Java, missing observer footer, or missing archive is an
   invalid harness outcome and must be repaired before another performance conclusion is drawn.

## Acceptance gate for a P0.2 sample

The run directory must contain a completed `p02-host.jsonl` (one header, samples, one footer),
`bootoptim-startup.log` with a single JVM start epoch and successful early/mod-entry snapshots, and the
archived `latest.log`/`debug.log`. `p02_correlate.py` must pass its provenance, endpoint and coverage
checks. A diagnostic sample is never a clean TTMM benchmark.

## End-to-end verification

`p02-harness-repaired-20260910d` is the first full verification after the
hardening work. It reached `finished` with `valid=true`, task result `0`, three
archived game diagnostic files, and a completed 13-sample host trace whose
footer says `process_exited`. `p02_correlate.py` accepted the archive without
issues. The low-intrusion observer used 437.5 ms CPU over the trace (about
0.12% of one core) and its slowest sample was 161.339 ms; this replaces the
previous WMI observer's 7.375 s CPU and 23.112 s worst sample. These figures
validate instrumentation overhead only; they are not an optimization claim.

## Sequential variation batches

`remote_laptop_p02_batch.ps1` runs isolated transactions sequentially. Each
run has its own state root (`batches/<batch-id>/runs/<batch-id>-NN/`), archives
its own completed evidence, restores production bytes before the next run, and
waits a configured interval (normally 60 seconds). The batch controller polls
only transaction state while Java is alive; it never tails game logs. Failed
runs are recovered and retained as failed evidence rather than overwritten.
All members of one batch use the same wrapper SHA, JVM contract and
`warm_same_boot` class, so they may be compared only with each other.

Two PowerShell-specific details are part of the batch contract:

- `$args` is an automatic variable.  A helper forwarding the transaction
  parameters must use a named parameter such as `$txArgs`; otherwise it can
  silently invoke the transaction with no arguments and leave a blank console
  instead of launching Prism.
- The per-run result must be created as one mutable `PSCustomObject` *before*
  it is appended to `results`.  Appending a conversion of an ordered dictionary
  creates a snapshot, so later `phase`, `valid`, and `postflight` assignments
  do not reach the batch summary even though each individual transaction is
  valid.  Individual state files remain authoritative if an older controller
  has this presentation defect.

## Ten-run warm-batch result — 2026-09-10

`p02-variation-batch-20260910b` completed ten individually valid, restored
diagnostic transactions under one warm-boot contract.  The controller summary
had the pre-fix presentation defect described above; the ten individual
`state.json` files and correlated archives are authoritative.

The diagnostic endpoint ranged from `377,155` to `407,052` ms (median
`385,075` ms).  The pre-entry interval was comparatively tight: `97,170` to
`108,924` ms (median `101,640` ms).  One post-entry sample reached `269,514`
ms versus a usual roughly `244--254` s interval.  It did not consume unusual
total Java CPU (`728,031` ms, within the observed normal range); its effective
CPU rate fell to `2.701` cores and GC time was `13,679` ms.  This correlates
with reduced execution availability plus a few seconds of GC, not with a new
deterministic game phase of comparable duration.

No run reproduced the historical multi-minute physical outlier.  The
low-intrusion observer itself is not a direct explanation for the slow sample:
its largest individual sampling costs occurred in different, non-outlier runs,
while total observer CPU stayed about 0.1% of one core.  This does not prove
host-wide causality because the observer intentionally does not inspect disk,
global scheduling or paging.

Disposition: P0.2 is no longer a blocker for evaluating architectural startup
work.  It remains a physical-risk watch item: reopen it only on a repeatable
large outlier, then capture a deliberately separate host trace/phase profile.
These probe-enabled samples are diagnostic correlation evidence, not clean
time-to-menu benchmark values.
