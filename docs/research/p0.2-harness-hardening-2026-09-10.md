# P0.2 harness hardening — 2026-09-10

## Scope

This is methodology evidence, not an optimization and not a time-to-menu result.
It records failures found while turning the laptop P0.2 investigation into a
reproducible diagnostic.

## Invariants

- Do not read Minecraft/Prism logs while a timed or diagnostic client is alive.
- Stage exactly one packaged bootstrap wrapper and validate its SHA-256 before launch.
- Bind Java to the interactive session, launch time, configured Java executable, creation time and
  validated JVM arguments before accepting a run.
- Treat process/observer failures as invalid evidence, never as performance values.
- Copy logs only after the validated Java process exits; restore the original wrapper and `instance.cfg`
  only when no owned Prism/Java process remains.

## Rejected instrument paths

1. `System.out` markers are not durable with Prism's `javaw`. P0.2 JVM snapshots now go through the
   Bootstrap startup report and the regular mod logger/report.
2. Detecting a launch only by `--gameDir`/instance-path text in `Win32_Process.CommandLine` rejected a
   real client that reached the menu. Prism's effective Java command does not reliably preserve that text.
   The runner instead uses session + launch-time + exact configured executable, then validates its full
   safe JVM-token contract before measurement.
3. An ordinary detached PowerShell child created avoidable lifecycle and `$Host` automatic-variable
   failures. The runner now registers the host observer as its own bounded interactive scheduled task
   after Java validation; it is not a child of the Java process or of an SSH session. This observer is
   diagnostic-only and disabled unless `P02HostProbe` is explicit.
4. `System.Diagnostics.Process.WaitForExit` was not reliable for this Java/Task Scheduler combination:
   a task could exit with code `1` or remain unfinalized after `javaw` had gone. The runner now polls a
   fresh process-table entry once per second, checking PID, executable process name and creation time.
   PID reuse or an unreadable identity invalidates the transaction; it never becomes a completed sample.
   The scheduled runner also writes `runner-output.txt` in the run directory so a non-zero task result
   has inspectable controller evidence without reading live Minecraft logs.
5. Prism owns the laptop heap through `OverrideMemory=true`, `MinMemAlloc` and `MaxMemAlloc`
   (currently 128/6144 MiB). Supplying `-Xms` or `-Xmx` through the transaction's `JvmArgs` opens
   Prism's warning dialog and invalidates unattended launch behavior. The transaction now rejects those
   flags before staging; heap changes belong to the Prism fields, not benchmark JVM arguments.

## Operator workflow

1. Dispatch the transaction and record only state/process/task status while Java is alive. Do not tail
   `latest.log`, `debug.log`, Prism output or the host observer file at this stage.
2. Poll at a bounded cadence (normally 10--15 seconds externally; the runner's exit check is one
   second). A visible window is not completion evidence. Java absence plus a final `finished`/`invalid`
   state is required.
3. Only after that final state, inspect `runner-output.txt`, wait for the P0.2 observer task to finish,
   archive logs, correlate the files and restore the original wrapper/configuration. A task result of
   non-zero, `measuring` with no live recorded Java, missing observer footer, or missing archive is an
   invalid harness outcome and must be repaired before another performance conclusion is drawn.

## Acceptance gate for a P0.2 sample

The run directory must contain a completed `p02-host.jsonl` (one header, samples, one footer),
`bootoptim-startup.log` with a single JVM start epoch and successful early/mod-entry snapshots, and the
archived `latest.log`/`debug.log`. `p02_correlate.py` must pass its provenance, endpoint and coverage
checks. A diagnostic sample is never a clean TTMM benchmark.
