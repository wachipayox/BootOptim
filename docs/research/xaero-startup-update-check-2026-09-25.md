# Xaero World Map startup version check — 2026-09-25

Status: **ACTIVE / runtime validation pending**. This is a compatibility experiment, not an integrated production result.

The prior closed diagnostic PR #100 observed an inclusive ~1.026 s `xaeroworldmap` deferred-work warning but could not attribute the task with its FML-boundary instrumentation. A later RRLS `MENU_READY` physical-PC run provides new, narrower evidence: after the early title gate opened at 17:02:52.673, the render thread entered `WorldMap.loadLater()` and spent a sampled 1.653 s frame gap in `xaero.map.misc.Internet.checkModVersion()` → `URLConnection.getContentLengthLong()`. The Xaero log reports `io exception while checking versions: Online mod data expired!` at 17:02:55.167, and NeoForge reports its deferred task took 1.425 s. The full render-thread stack is preserved in `C:\BootOptimBench\rrls-menu-ready-stage-20260924\rrls-menu-freezes-blur-reload-review-20260925.log`; corresponding run log is `latest-blur-reload-review-20260925.log`. This identifies the actual synchronous network work that #100 could only hypothesize. It is a visible first-menu frame stall, not a time-to-menu critical-path saving claim.

Bytecode inspection of the installed Xaero World Map 1.41.0 JAR shows that `loadLater()` calls `Patreon.checkPatreon()` and then `Internet.checkModVersion()` before setting the update-notification state and continuing map initialization. The version checker performs a blocking URL request with 900 ms connect/read timeouts; the `UPDATE_NOTIFICATIONS` option is read only after that request begins. Thus turning off notifications alone would not remove the stall, and turning off XaeroLib's global Internet permission would affect more than this check. The same run's two F3+T reloads do not call `checkModVersion()` again. Their late render-thread stalls are separate atlas/shader/MoreCulling/FancyMenu apply work, recorded in the RRLS/FancyMenu research entry.

Candidate: on exact Xaero World Map **1.41.0** only, BootOptim omits the `checkModVersion()` invocation from `WorldMap.loadLater()` via an optional MixinExtras `WrapOperation`. All other Xaero initialization, Patreon checking, map use, and Internet functions remain unchanged. Property `-Dboot_optim.xaeroSkipStartupUpdateCheck=false` restores the stock call. A missing/unknown Xaero version retains stock behavior. The observable tradeoff is loss of World Map's automatic update notification for this version; the user explicitly requested considering removal of that check after seeing the attributed stall. There is no claim of faster resource reload or improved F3+T behavior from this change.

Validation required before promotion: compile/package and exact-pack startup smoke; confirm the skip marker and absence of new Mixin failures; physical first-menu frame trace; first singleplayer/multiplayer world and first Xaero map use. Compare the same process/BootOptim origin and menu endpoint if reporting startup time. No startup A/B or visual/map validation has yet been completed. Reopen/disable on Xaero version change, unexpected map behavior, or if physical evidence shows the network stall no longer occurs.
